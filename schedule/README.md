# 志愿者排班（tool-schedule）

按报名先后为志愿者分配岗位，支持在已有排班上增量调整。桌面版（tkinter）搬过来
的，`core.py` 的算法几乎原样，`gui.py` 整个丢掉换成 Vue。

## 协作与历史

**协作者和创建者权限基本一致**（能改、能导出、能再拉人），**唯独删不掉项目**。
不分级是因为分级只会带来「他改不了这一格，得去找建项目的人」，而这个工具的场景
就是一个活动的几个负责人一起排班；删除单拎出来是因为它不可逆，而且会把历史版本
一起 CASCADE 掉——历史本来是给误操作兜底的，删项目恰恰把那张网也撤了。

判定在 `store.require_owner`，回 403 不回 404：协作者本来就看得见这个项目，
没有存在性需要藏，回 404 只会让人以为项目没了。

**只能靠邀请链接加人，没有「搜昵称直接加」。** 两条理由：这个服务压根不认识
社区里的其他用户（`auth.py` 只做「拿 cookie 换 user_id」）；更要紧的是加人等于
把全员的身份证号交出去，搜索列表里手滑点错一个人就收不回来，而链接是你主动
发出去的。链接 7 天过期、随时可撤销、能看见被用过几次。

**同一时刻只有一个人能改。** 整份状态 PUT + 乐观并发这套模型单人用很省心，
多人用就成了主要痛点：两件毫不相干的事也会互相 409，而且是写完半天才被打回。
所以加了编辑占用：别人占着时界面是只读的，5 分钟没动作自动放开，等不及可以
接管（接管会留痕——之后的改动在历史里记的是接管者）。

**历史版本最多 50 版**，重要节点（应用排班、导入、清空、改规则）每次单独存，
零碎的手工微调按 3 分钟窗口攒成一版——不这么分的话 50 版可能只覆盖十分钟的
连续操作，回不到昨天那一版。恢复是「往前写一版，内容等于旧版」，不回退版本号
（版本号是乐观并发的依据）。项目删除时历史、成员、邀请一并 CASCADE 清掉。

**登录就能用，没有白名单**——和 bv2008 不一样：那个会代你去操作志愿北京上的团体
数据，动的是别人的平台，所以要审批；这个只在你自己的项目里算数，算错了也只影响
你自己那张表。

## 和 bv2008 的差别

| | bv2008 | schedule |
| --- | --- | --- |
| 外部依赖 | 真浏览器 + 志愿北京 | 无，纯计算 |
| 并发 | 单槽排队（一个 Chromium） | 随便并发，只限「一个人同时算一次」 |
| 权限 | 白名单审批 | 登录即可 |
| 状态 | 一次性会话 | 长期项目，存库 |

所以 bv2008 里最复杂的那几坨——单槽队列、会话状态机、WebSocket 事件流、断线重连、
闲置回收——这里一样都没有。

## 数据

一张 `projects` 表，整份状态存 JSONB（`core.Project.to_dict()` 原样，序列化格式
一个字没改）。不拆成岗位/志愿者/报名/排班四张表：这个工具从来不会「只查某个
志愿者」，求解、导出、候补队列每一件事都要把整份状态读进内存，拆表只换来一堆
join 和一份必须和 `core.py` 同步演进的映射代码。

⚠️ 里面有**姓名、身份证号、联系方式、微信**。对应的约束：

- 所有读写都按 owner 过滤，`store.py` 是唯一入口；查不到和不是你的都回 404
  （区分开的话，拿 UUID 逐个试就能问出别人有哪些项目）；
- 社区管理员也看不到别人的项目——没有「看全部」的接口；
- 180 天不动自动删除，到期前 14 天提示，可续期。删是真删；
- 屏幕上的表格不显示身份证号，导出的 xlsx 里有。

## 求解

规则的完整清单、哪些固定哪些可配，见 **`RULES.md`**。这一节只说时间。

`find_slot` 的回溯增广是求解器里唯一指数级的地方——「腾位置时最多连锁挪几个人」，
每层要试「岗位里的每个人 × 他报过的每个其他岗位」。深度 6 时：

    岗位 12 / 人 40 / 名额 2 / 人均报 3 个岗位  → 0.6 秒
    岗位 12 / 人 40 / 名额 2 / 人均报 6 个岗位  → 十几分钟都算不完

人均报 6 个岗位一点都不极端。所以**主段的深度是 2**（10² 量级的分支，同样的表
零点几秒就完），超时了退到深度 1，两段各 60 秒、互不挪用。

深度值不值那些时间，量过：14 岗位 / 30 人 / 名额 1~3 / 人均报 2~4 / 三成岗位有
性别要求 / 带冲突图，120 个随机实例，depth=6 和 depth=1 排进去的人次**完全相同**
（3189 对 3189），耗时 0.48 秒对 16.38 秒。不压到 1 是因为有一类「两步腾位链」
只有深度 ≥2 走得通，见 `RULES.md` 7.2。

`solve_guard.py`：一个人同时只能算一次。前端会禁按钮，但那只挡得住同一个页面上的
连点。

## 接口

动作走 HTTP，没有 WebSocket。划分原则是**服务端只做客户端做不了的事**——解析
表格、跑求解器、生成 xlsx；锁定/调岗/勾冲突矩阵这些纯改状态的，客户端改完整份
`PUT` 回来（带版本号做乐观并发）。

| | |
| --- | --- |
| `GET /me` | 你是谁 + 保留天数 + 求解上限 |
| `GET /projects` | 项目列表（**不含 data**） |
| `POST /projects` | 新建，可带示例数据 |
| `GET /projects/{id}` | 整份状态 + 派生视图 |
| `PUT /projects/{id}` | 整份状态存回（乐观并发） |
| `PATCH /projects/{id}` | 改名 |
| `POST /projects/{id}/renew` | 续期 |
| `DELETE /projects/{id}` | 删除 |
| `POST /projects/{id}/import/positions` | 导入岗位表 |
| `POST /projects/{id}/import/signups` | 导入报名表 |
| `POST /projects/{id}/solve` | 排班。`apply=false` 预览、`true` 应用 |
| `POST /projects/{id}/rules/preview` | 拿一份规则配置试算一次，**不落库**，只报后果 |
| `GET /projects/{id}/export` | 导出 xlsx（**含身份证号**） |
| `GET /sample` | 示例表格 |
| `GET /projects/{id}/versions` | 历史版本列表（不含 data） |
| `GET /projects/{id}/versions/{vid}` | 某一版的内容 + 派生视图，只读 |
| `POST /projects/{id}/versions/{vid}/restore` | 恢复到某一版（往前写一版，不回退版本号） |
| `GET /projects/{id}/collab` | 协作者 + 谁正占着编辑权 |
| `POST /projects/{id}/lock` | 占住编辑权（`?force=1` 接管） |
| `POST /projects/{id}/invites` | 生成邀请链接 |
| `POST /invites/{token}/accept` | 拿链接加入。**不在 /projects 下面**——加入前你还不是这个项目的人 |

派生视图由服务端算，见 `views.py`——岗位统计 / 排班表 / 候补队列 / 报名记录 /
**零岗位名单** / **标签值域** / **条件体检**。三条理由：

- 候补队列的落选原因和求解器共用一套判据，前端照抄一遍迟早会漂；
- 条件的人话说明（`conditions.describe`）三处共用，各画各的会在「≥ 还是 >」
  这种地方对不上；
- 候补**排位**必须跟着规则配置里的轮次顺序走，两边各写一份的话，页面上写着
  「你是第 3 位候补」而实际排班按另一套来，那是骗人。

## 前端

`apps/web/src/views/tools/schedule/`。组件叫 `VolunteerScheduleView.vue` 而不是
`ScheduleView.vue`——平台已经有一个 `/course/schedule` 全校课程表，同名文件在构建
产物和调用栈里分不清。

## 本地开发

```bash
pip install -e .
export SCHEDULE_DATABASE_URL=postgresql://tool_schedule:...@127.0.0.1:5433/rucommunity
alembic upgrade head
uvicorn app.main:app --port 9372 --reload
```

跑测试：接口那一组需要真的 Postgres（JSONB、乐观并发、按 owner 过滤，用假仓库
测不出真东西），没配就自动跳过。

```bash
SCHEDULE_TEST_DATABASE_URL=$SCHEDULE_DATABASE_URL pytest
```
