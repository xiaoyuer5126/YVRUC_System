## 1. 数据模型改动

### 1.1 `Position`

| 字段 | 状态 | 说明 |
| --- | --- | --- |
| `pid` / `name` / `time_note` | 不变 | |
| `quota` | 不变 | 名额上限。**含组长**——这个岗位一共站几个人 |
| `min_quota` | **新增** | 最低人数。`0` = 不设 |
| `requirements` | **改类型** | `dict` → 条件树（见第 6 节）。必选条件 |
| `preferences` | **新增** | **有序**条件列表。优先条件，靠前的优先级高 |
| `leader` | **新增** | `{count, conditions}`。`count=0` = 该岗位不设组长 |
| `req_note` | **新增** | Excel「要求」列的原文，只读参照，不参与求解 |
| `reserve_note` | **并入** | 原「保底要求」预留字段，语义上就是最低人数的备注，并进 `req_note` |

约束校验：`leader.count > quota` 拦下；`min_quota > quota` 拦下。

### 1.2 `Assignment`

| 字段 | 状态 | 说明 |
| --- | --- | --- |
| `pid` / `vol_key` / `status` / `forced` | 不变 | |
| `role` | **新增** | `""` = 普通槽，`"leader"` = 组长槽 |

### 1.3 `Project.to_dict()`

新增顶层键 `rules`（见第 5 节）。`version` 记 `2`。

### 1.4 报名表格式：不变

**报名不分角色。** 报名表还是「每岗位一列 0/1」，谁能当组长由 `leader.conditions` 判定。

「愿不愿意当组长」本来就该是报名表里的一个标签列（如 `是否愿任组长=是`），
条件机制天然覆盖它——不需要为组长改报名表格式。

## 2. 规则全表

按**规则作用在算法的哪一层**分组。这个分组不是为了好看：不同层的规则根本不在同一个排序键里，
**「拖动排序」只在层内有意义**。

### H 层 · 硬约束（判定一次放置是否合法）

| | 规则 | 可配性 |
| --- | --- | --- |
| H1 | `LOCKED` 行绝不改动，且求解前先占掉名额 | 固定 |
| H2 | 只能排到本人报过名的岗位 | 固定 |
| H3 | 满足岗位的必选条件（`requirements`） | 固定 |
| H4 | 不与已获岗位时间冲突（`conflicts`） | 固定 |
| H5 | 不超名额上限（`quota`） | 固定 |
| H6 | 不掉岗：已获岗位的人只会被换岗 | 固定 |
| H7 | 同人同岗位不重复 | 固定 |
| H8 | 人工 `forced` 可突破 H4/H5 | 固定 |
| H9 | 组长槽需满足 `leader.conditions` | 固定 |
| H10 | 不超组长槽容量（`leader.count`） | 固定 |

**整层固定，一个开关都不给。** 这不是「偏好」，是「什么叫一份有效的排班」的定义。

H4 看着像可以放宽，但冲突图本来就是用户自己在矩阵里勾的——不想它生效，不勾就是了。

界面上建议**列出来但置灰**，配一句说明。H1 和 H6 是运营方敢用这个工具的前提，
看得到比看不到更让人放心。

### O 层 · 轮次顺序（轮到谁挑）

现在是 `core.py` 主循环里的 `(已获岗位数, 最早未满足报名时间)`。

| | 规则 | 可配性 | 默认 |
| --- | --- | --- | --- |
| O1 | 每轮每人至多新增一个岗位 | 可开关 | 开 |
| O2 | 已获岗位数少者优先（摊平） | 可开关 + 可与 O3 换序 | 开，在 O3 之前 |
| O3 | 报名时间早者优先（先到先得） | **固定存在，位置可变** | 在 O2 之后 |
| O4 | 报名岗位数少者优先 | 可开关 | **关** |

**O3 不给关闭开关。** 它是这个工具的公平性根基，也是唯一能对志愿者公开交代的规则；
允许关掉等于允许暗箱操作。但它和 O2 的相对位置是有意义的选择：

- `O2 → O3`（默认）：所有人拿到第 1 个岗位之前，没人拿第 2 个。
- `O3 → O2` + 关 O1：纯先到先得，第一个报名的人一次把他报的岗位全部拿满。

O4 的用意：只报了一个岗位的人排不上就什么都没有，报了六个的人挑剩下还有五个机会。
默认关，因为它和 O3 有张力（会让晚报名但选择少的人插到早报名但选择多的人前面），
得让用户明确选。

### C 层 · 候选岗位排序（轮到这个人时，他先挑哪个岗位）

现在是 `cand_key` 五元组。

| | 规则 | 可配性 | 默认位置 |
| --- | --- | --- | --- |
| C1 | 未达最低人数的岗位优先 | 可开关 + 可排序 | 1 |
| C2 | 缺口率大的岗位优先 | 可开关 + 可排序 | 2 |
| C3 | 同批增益大的优先（`cohorts`） | 可开关 + 可排序 | 3 |
| C4 | 上一版组合优先（增量稳定） | 可开关 + 可排序 | 4 |
| C5 | 别人补不上的岗位优先（`others_want`） | 可开关 + 可排序 | 5 |
| C6 | 本人符合该岗位优先条件的靠前 | 可开关 + 可排序 | 6 |
| C7 | 有组长资格时优先占组长槽 | 固定（跟随组长功能） | — |
| C8 | 岗位表原顺序 | **固定垫底，永远最后一位** | 末 |

C8 必须永远垫底，否则同一份数据两次求解可能给出不同结果。

C5（`others_want`）是 O(人数) 的，**开着它本身就有成本**，人多岗位多时它是热点；
前后挪不会更慢，但关掉能明显提速。

> **C 层配置化的风险比 O 层低得多。** 见第 8 节：在深度足够的前提下，
> C 层规则不影响「谁能拿到岗位」，只影响「拿到哪个」。

### G 层 · 腾位增广（`find_slot` 内部）

| | 规则 | 可配性 |
| --- | --- | --- |
| G1 | 被挪走的人优先去「当场有空位」的岗位 | 固定 |
| G2 | 其次去上一版待过的岗位 | 固定 |
| G3 | 最后按岗位表顺序 | 固定 |

**整层不暴露给用户。** 「腾位置时被挪走的人该往哪去」的排序是实现细节，
用户没有直觉去判断它，暴露出来只增加配错的机会。

连锁深度是**独立的数值参数**，不进规则系统，见第 7 节。

### P 层 · 后处理 pass

| | 规则 | 可配性 |
| --- | --- | --- |
| P0 | **保底重试**：对 0 岗位的人用大深度再试一次 | 固定 |
| P1 | **最低人数补位**：从「抽走一人仍在线上」的岗位调人去补缺口 | 跟随最低人数功能 |
| P2 | **组长补位**：岗内合格者从普通槽升组长槽，腾出的普通槽再补 | 跟随组长功能 |
| P3 | **同批换人**：现有 `_improve_cohort` | 可开关 |

**执行顺序固定为 P0 → P1 → P2 → P3，不可配。** 它们会互相破坏：
P1 调人可能拆散同批，P2 升人可能让某岗位跌破最低线。固定顺序 +
「每个 pass 只做不破坏前面 pass 结果的改动」是唯一能推理清楚的做法。
同批放最后，因为它是纯偏好，被牺牲掉损失最小。

这一层有一条贯穿性的不变式，值得单独记住：

> **P0 决定「谁有岗位」，P1–P3 只决定「谁在哪个岗位」。**
> P1/P2/P3 都不增不减已排人次，也不让任何人掉岗。

P1、P2、P3 结构完全同构（不掉岗、不动 LOCKED、严格改善才换、有 guard 上限），
**抽成一个共用的「重分配」框架**，别照着 `_improve_cohort` 复制两遍。

已知的近似：P1 把人从富余岗位调走后会留下空位，理论上可能让 P0 再救回一个人。
不做迭代——迭代要证明收敛，成本高于收益。这是明知的、可接受的近似。

### S 层 · 阶段控制

| | 规则 | 可配性 |
| --- | --- | --- |
| S1 | 优先条件分两阶段放行 | 可开关（默认开，跟随优先条件） |
| S2 | 组长槽先于普通槽填 | 固定（跟随组长功能） |

**S1 是「优先条件」真正起作用的地方。** 光在 C6 加一个排序分量效果很弱——
C 层排的是「这个人挑哪个岗位」，而优先条件想管的是「这个岗位要谁」，方向不对。

做法：主循环加一个 phase 变量。第一遍只允许符合优先条件的人进带优先条件的岗位，
第二遍才开放给所有人。改动小、结果可预测。

**不做抢占式**（符合优先条件的人把不符合的挤走）。虽然 `find_slot` 天然支持，
但它破坏「先到先得」的直觉，且会放大唯一那个指数级搜索的空间。

### V 层 · 派生视图排序

| | 规则 | 可配性 |
| --- | --- | --- |
| V1 | 排班表岗内按报名时间（`schedule_view`） | 固定 |
| V2 | 候补排位键（`build_queue`） | **必须跟随 O 层配置** |
| V3 | 报名记录按已获数降序、姓名（`signup_view`） | 固定 |

> ⚠️ **V2 是配置化最大的一笔暗账。** 候补排位现在和主循环用的是同一个键
> `(已获岗位数, 报名时间)`。O 层顺序一旦可配，V2 必须跟着变——否则页面上写着
> 「你是第 3 位候补」，实际排班却是另一套顺序，那是在骗人。
>
> 实现上：O 层配置必须同时喂给求解器和 `build_queue`，不能各写一份。

## 4. 预设方案

9 项可排序意味着几十万种组合，**不可能逐一测试，也不可能逐一解释**。
所以界面的默认入口是预设，「自定义」收在展开里。

| 预设 | O 层 | C 层 | 适用 |
| --- | --- | --- | --- |
| **均衡**（默认） | O1 开，`O2 → O3` | `C1 → C2 → C3 → C4 → C5 → C6` | 大多数活动 |
| **先到先得优先** | O1 关，`O3 → O2` | `C2 → C6 → C4 → C3 → C5`，C1 关 | 报名即确认的活动 |
| **保底优先** | O1 开，`O2 → O3`，O4 开 | `C1 → C6 → C5 → C2 → C3 → C4` | 死保最低人数和组长，牺牲稳定性 |

### 自定义模式：保存前强制试算

拖完顺序**不能直接保存**（保存按钮禁用，直到试算结果和当前草稿对得上）。
`POST /projects/{id}/rules/preview` 在本项目数据上跑一次真求解器，报出后果：

- 有几个岗位达不到最低人数（列出 pid）
- 有几个组长槽填不满（列出 pid）
- 有多少人一个岗位都没有
- 与当前排班相比有多少人变动、其中多少人换岗或被移除

**走的是求解器本身，不是另写一套估算**——估算和实际不一致的话，这一步反而害人。

切换预设不用试算：那三套是被测过的组合，点了直接生效。

理由：贪心算法在某些组合下会给出明显糟糕的结果（比如 C4 增量稳定置顶 + C1 关闭，
会出现一堆岗位达不到最低线但算法认为「已经没有进展」就停了），
而用户不会认为是自己配错了，只会认为是程序算错了。

### 存储

规则配置进项目 `data` 的 JSONB（`to_dict()` 加 `rules` 键），**不单开表**——
和现有「整份状态 `PUT` 回来 + 乐观并发」的架构一致，版本号天然覆盖它。

实现上，`cand_key` 从硬编码元组改成**在 `solve()` 开头按配置编译出一个闭包列表**。
注意是编译一次，不是每次查字典——它在热循环里。

## 5. `rules` 结构

```jsonc
{
  "preset": "balanced",              // balanced | first_come | floor_first | custom
  "order":     [                     // O 层，有序
    {"key": "round_cap",   "enabled": true},   // O1
    {"key": "spread",      "enabled": true},   // O2
    {"key": "signup_time", "enabled": true},   // O3，enabled 恒 true，不可改
    {"key": "few_options", "enabled": false}   // O4
  ],
  "candidate": [                     // C 层，有序
    {"key": "min_quota",  "enabled": true},    // C1
    {"key": "gap",        "enabled": true},    // C2
    {"key": "cohort",     "enabled": true},    // C3
    {"key": "stable",     "enabled": true},    // C4
    {"key": "scarce",     "enabled": true},    // C5
    {"key": "preference", "enabled": true}     // C6
  ],
  "toggles": {
    "cohort_swap":      true,        // P3
    "preference_phase": true         // S1
  }
}
```

`preset` 只是记录用户选了哪套，**求解只看 `order`/`candidate`/`toggles`**——
换预设 = 把对应的三段整体覆盖进去。这样自定义之后仍然能显示「基于均衡改过」。

服务端校验：`signup_time` 必须存在且 `enabled: true`；key 集合必须完整（不能少项也不能有未知项）。

## 6. 条件系统

### 6.1 分工：数值从 Excel 导，条件在网页设

**岗位条件不从 Excel 解析。**

理由不只是省掉一个解析器：在 Excel 里写条件的人**看不到标签的实际取值**，
写出来的十有八九对不上真实数据（写「性别=女」而表里是「女生」）。
而主办方在表格里实际会写的是自然语言——「女生优先，最好有急救证」——那本来就不该被解析。
让它保持自然语言，人对照着在网页里点出条件，中间那道翻译由人来做，比由解析器来做靠谱得多。

| Excel 岗位表列 | 处理 |
| --- | --- |
| 岗位ID / 岗位名称 / 时间说明 | 照旧导入 |
| 名额 / **最低人数** / **组长人数** | 照旧导入（数字没有歧义） |
| 要求 / 保底要求 | 存进 `req_note`，**只读参照**，在条件编辑器旁边显示 |

> ⚠️ **重新导入岗位表不能冲掉网页配好的条件。**
> 现在 `import_positions` 遇到已存在的 pid 是整体覆盖 `project.positions[pid] = pos`，
> 必须改成字段级合并：表里有的字段更新，`requirements` / `preferences` / `leader` 原样保留，
> 并在警告里说清「岗位 P04 已存在，已更新名额与时间说明，条件配置保留」。

`parse_kv` / `format_kv` / `split_multi` **不删**——志愿者标签还是 `key=value` 格式，
导入和显示都还要用。只是不再用于岗位要求。

### 6.2 条件树

存储与求值的唯一格式。前端画成可视化构建器：选标签 → 选运算符 → **从该标签的已有取值里选值**。

```jsonc
{
  "all": [
    {"tag": "性别", "op": "eq", "value": "女"},
    {"any": [
      {"tag": "年级", "op": "eq", "value": "2023"},
      {"tag": "年级", "op": "eq", "value": "2024"}
    ]},
    {"tag": "服务时长", "op": "gte", "value": 20}
  ]
}
```

**只允许两层**：顶层 `all`，里面可以放 `any` 组。覆盖 99% 的需求，UI 不会变成树编辑器。

运算符集合：

| op | 语义 | 比较方式 |
| --- | --- | --- |
| `eq` / `ne` | 等于 / 不等于 | 字符串 |
| `in` / `not_in` | 属于 / 不属于（多值） | 字符串 |
| `contains` | 包含 | 字符串 |
| `gt` / `gte` / `lt` / `lte` | 大于 / 不小于 / 小于 / 不大于 | 数值 |
| `between` | 介于 | 数值 |
| `filled` / `empty` | 已填写 / 未填写 | — |

`filled` / `empty` 别漏——「有没有交健康证明」这类判定很常用。

### 6.3 类型问题：由运算符决定，不要猜

标签值全是字符串（`_cell_str` 进来就转字符串了）。

- **字符串类**：做规范化——去首尾空格、全角转半角、统一小写。
- **数值类**：两边都试着转 `float`，**转不动就判不满足，并记一条警告**。

那条警告是重点。数据脏是常态（`20小时`、`20 h`、`二十`），静默判 `false`
会让人排完了才发现少了一半人，还查不出原因。诊断走单独的 `check()`，
`match()` 是热路径，一个诊断都不做。

**忽略大小写不做成开关**（原计划是「可选」，实现时定死了）。中文没有大小写，
英文标签（`Female` / `female`）分大小写没有任何正当用途，而多一个没人看得懂的
开关只会多一种配错的方式。

**条件里的阈值则相反：填错当场拒。** `服务时长 ≥ 二十` 在保存时就抛错，不留到
求解时静默判 `false`——那是人在网页上填的一个数，没有「脏数据」一说，
静默容忍的表现是「这个岗位一个人都排不上」而没人知道为什么。

### 6.4 求解前的条件体检

扫一遍所有条件 × 所有志愿者，把**无法求值**的组合列出来：

> 岗位 P04「颁奖礼仪」的条件「服务时长 ≥ 20」：李四的「服务时长」值是「20小时」，无法比较，判为不满足。

### 6.5 标签值域面板

列出每个标签在报名表里出现过的所有取值和人数。用户一眼看到「性别」列里同时有
「女」「女生」「Female」。**没有这个，条件写得再强也白搭。**

### 6.6 标签归一化（第二期）

允许把「女生」「Female」映射到「女」，项目级的 `tag_aliases: {标签: {原值: 归一值}}`。
**收益比运算符还大**——脏数据才是主要矛盾——但它是独立功能，不该卡住主线。

## 7. 深度与时间预算

### 7.1 深度是什么

`find_slot` 的连锁腾位层数。**它只影响一件事：能不能把人塞进已经满员的岗位。**
岗位有空位时第一句就放进去了，深度根本用不上。

- `depth=0`：不挪任何人，只填空位
- `depth=1`：把满员岗位里的人挪到一个**当场有空位**的岗位
- `depth=2`：那个人要去的岗位也满了，就再挪一层
- `depth=k`：最多连锁挪 k 个人

代价是每层 `(岗位内 AUTO 人数) × (每人可用备选岗位数)` 条岔路。名额 2~3、人均备选 3~5
的话每层 6~15 条，`depth=2` 约 10² 条叶子路径，`depth=6` 是 10⁶ 量级。

实测（2026-08，14 岗位 / 30 人 / 名额 1~3 / 人均报 2~4 / 三成岗位有性别要求 / 带冲突图，
120 个随机实例）：`depth=6` 与 `depth=1` **排进去的人次完全相同**（3189 对 3189），
耗时 0.48 秒对 16.38 秒。

### 7.2 定下来的参数

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 主深度 | **2** | 覆盖「挪一个人，他还得再挤走一个」这类真实链条 |
| 主段预算 | **60 秒** | |
| 降级深度 | **1** | 主段超时才用。多项式，不会爆炸 |
| 降级预算 | **60 秒** | 独立预算，不从主段挪用 |
| 保底重试深度 | **5** | 只对 0 岗位的人用 |
| 保底重试预算 | **20 秒** | 独立预算 |

最坏情况一次排班占一个核 **140 秒**（主段烧满超时 60 + 降级段 60 + 降级段的保底
重试 20）。主段超时时它那趟保底重试压根没开始（超时在 sweep 里就抛了），所以
rescue 只算一份。nginx 的 180 秒读超时仍有余量。

> ⚠️ **保底重试实测一个人都没多救到。** 300 个随机实例，含名额全 1、人数贴着
> 岗位数、志愿高度重叠这种最容易出长链的形状，`depth=5` 重试和不重试的零岗位
> 人数逐个相等，0 个实例受益。原因大概是外层那个「反复重排直到没有进展」的循环
> 本身就已经收敛到最大可匹配集合——剩下的人是真的没位置，不是深度不够。
>
> 留着的理由只是它便宜（实际项目规模下 +0.01~0.7 秒）、有独立预算、有快照兜底
> 不会弄坏结果。**它是保险，不是能提升排班率的东西**；哪天要砍成本，第一个砍它。

为什么主深度选 2 而不是 1：这类链条在**名额小、接近饱和**时最常出现，而「小组长」
正好制造大量容量 1~2 的槽位。举例——

> P1、P2 名额各 1，甲在 P1、乙在 P2，P3 空着。甲报了 P1/P2，乙报了 P2/P3，丙只报了 P1。
> `depth=1`：甲想挪去 P2，P2 满，失败 → 丙空手。
> `depth=2`：甲→P2，乙→P3，丙进 P1 → 三个人都有岗位。

### 7.3 保底重试（P0）的两条硬要求

**(a) `assignments` 必须建索引，这是 `depth=5` 的前提。**

现在 `unplace` 用 `assignments.remove(a)` 是 O(n) 全表扫，`find_slot` 开头那句
`[x for x in assignments if x.pid == pid and ...]` 也是 O(n)——**每个递归节点扫两遍全表**。
`depth=5` 有 10⁵ 量级节点，乘上 100 条排班就是 10⁷ 次操作，纯 Python 下要好几秒。

改成 `by_pid: {pid: list}` 索引 + 标记删除。`depth=2` 时这笔开销藏得住，`depth=5` 时藏不住。

**(b) 保底重试超时不能算失败。**

现在 `SolveTimeout` 的语义是「一无所获」（`core.py` 里特意说明不返回半成品）。
但 P0 是**锦上添花的额外 pass**：它算不完应该保留主段结果照常返回，
只在界面上说一句「有 3 人未能通过深度重排补上」。

无论主段还是降级段，P0 都照跑，用同一套 depth=5 / 20 秒。

### 7.4 并发

`solve_guard.py` 只限「一个人同时只能算一次」，**没有全局并发上限**——
10 个人同时排班就是 10 个核 × 80 秒。当前规模应该没事，但要知道这件事。

## 8. 公平性：早报名者能拿到什么保证

这是运营方最容易被追问的地方，也是文案必须写准的地方。

### 8.1 成立的部分

轮次顺序是 `(已获岗位数, 最早未满足报名时间)`。**第一轮所有人都是 0 个岗位，
所以第一轮就是纯按报名时间处理。** A 比 B 早，A 一定先被处理，此时 B 还没拿走任何东西；
O2（摊平）又保证所有人拿到第 1 个岗位之前没人拿第 2 个。因此：

> **晚报名者绝不可能抢走早报名者的第一个岗位。**

还有一条更强的性质，它是 C 层敢放开配置的根据：

> **在深度足够的前提下，C 层规则（缺口率、同批、增量稳定、稀缺岗位）
> 不影响「谁能拿到岗位」，只影响「拿到哪个岗位」。**

因为 C 层只决定 A 先挑走哪一个，而增广能把挑错的重新调开——只要存在一种让 A 和
所有更早的人同时有岗位的排法，算法就能找到它。这句话可以直接写进帮助文案。

### 8.2 不成立的部分：客观限制（与排序无关）

1. **志愿面窄** —— A 只报了一个岗位，而它被更早的人或 LOCKED 占满了。
   **总名额充足不代表 A 有得排**：大家只跟自己报过的岗位竞争，全局余量补不到局部。
2. **不符合必选条件 / 与已获岗位冲突** —— H3 / H4。
3. **LOCKED 预占** —— 人工锁定在求解前就占了名额，H1 优先于一切。
4. **增广深度不足** —— 存在一条长于深度的重排链能把 A 塞进去，算法找不到。
   **这是唯一由算法近似性造成的意外破例**，P0 保底重试就是为它准备的。

### 8.3 不成立的部分：新规则**故意**打破（必须在界面上说清楚）

| 规则 | 破例方式 |
| --- | --- |
| **S1 优先条件分阶段** | A 早报名但不符合优先条件，B 晚报名但符合 → B 先拿。**这就是「优先分配」的定义**，不是 bug |
| **C7 / S2 组长槽优先** | A 报的岗位普通槽满了、组长槽空着但 A 没资格 → 晚报名的合格者拿到 |
| **O4 少志愿者优先**（默认关） | 明确把「报名岗位数」排在「报名时间」之前 |
| **「先到先得优先」预设** | 反过来：早报名者一次拿满全部志愿，晚报名者可能一个都没有 |

**不会**破例的：P1 最低人数补位调的是「人在哪个岗位」，人不掉岗，
所以不影响「有没有岗位」，只影响「在哪个」。

## 9. 解释能力（和规则同等重要）

规则从 4 条涨到 20 多条，用户必然会问「为什么他排上了我没有」，
答案会变成「你在第 3 条规则上排他后面」——**这句话必须由程序说出来**。

没有这一层，规则越多工具越像黑箱，用户越不信任，最后还是回去手工排，那这些功能就白做了。

### 9.1 零岗位名单（先做这个）

求解后直接列出所有一个岗位都没拿到的人，**按报名时间排序**，逐个标原因：

志愿全满 · 不符合必选条件 · 与已获岗位冲突 · 被优先条件让位 · 被 LOCKED 占位 · 算法未能腾出

这是运营方最容易挨骂的地方，比逐条规则的解释有用得多。

### 9.2 落选原因扩展

现在只有三种（`REASON_FULL` / `REASON_CONFLICT` / `REASON_REQ`），要扩到：

| 原因 | 触发 |
| --- | --- |
| 不符合必选条件 | H3 |
| 与已获岗位冲突 | H4 |
| 名额已满且无法腾位 | H5 + 增广失败 |
| **因优先条件让位** | S1 |
| **因摊平被推迟** | O2（别人还没拿到第一个岗位） |
| **条件无法求值** | 6.3 的数据格式问题 |

### 9.3 排班解释（第二期）

对每个 (人, 岗位) 记录他在第几轮、被哪条规则挡下。数据量不大（人数 × 报名岗位数），
可以在求解时顺手记，不落库，跟派生视图一起返回。

## 11. 一键清空

纯前端 + 现有 `PUT`，不需要新接口——都是「纯改状态」，符合 README 里那条划分原则。

| 动作 | 连带 |
| --- | --- |
| 清空岗位 | 必须连带清冲突图、同批图、报名项、排班。**循环调用现有的 `remove_position`**，别自己写一遍 |
| 清空报名 | 连带清排班，否则派生视图会出现「排了一个不存在的人」 |
| 清空自动排班 | 保留 `LOCKED` 行 |
| 清空全部排班 | 含 `LOCKED` |

排班拆成两个动作，是因为 `LOCKED` 是人工确认过的，一次误点损失很大。

`prev_pairs` **不清**。留着的话，清空后重排，变更表显示的是「相对上一版已应用排班的变化」，
恰好是人想看的。

## 12. 测试策略

现在的测试（`test_solver.py` / `test_core.py`）全在测超时和降级，
**没有一条断言规则语义**。规则从 4 条涨到 20 多条之前，这个缺口必须先补。

最有价值的不是逐条规则的单元测试，而是 **property-based 的不变式测试**：
随机生成大量项目 × 随机生成合法配置，断言下面这些**在任何配置下都成立**。

| 不变式 | 对应 |
| --- | --- |
| `LOCKED` 行逐字不变 | H1 |
| 没有人排到没报名的岗位 | H2 |
| 所有非 `forced` 行满足必选条件 | H3 |
| 所有非 `forced` 行无时间冲突 | H4 |
| 所有岗位不超名额、不超组长槽 | H5 / H10 |
| 求解前有岗位的人，求解后仍有岗位 | H6 |
| 同输入 + 同配置 → 逐字相同的输出 | C8 确定性 |
| P1/P2/P3 前后已排人次不变 | P 层不变式 |
| 候补排位与实际排班顺序一致 | V2 耦合 |
| 无论怎么配，都不会抛异常 / 不会死循环 | 兜底 |

这类测试是唯一能兜住组合爆炸的东西——9 项可排序规则有几十万种组合，
逐一写用例是不可能的，但「无论怎么配这十条都成立」是可以验证的。

单独还需要的定点测试：

- 7.2 里那个 `depth=1` 失败、`depth=2` 成功的三人例子
- 重新导入岗位表不冲掉网页条件（6.1）
- 保底重试超时不影响主段结果（7.3b）
- 组长槽含在 `quota` 内的边界：`leader.count == quota`、`leader.count > quota`
