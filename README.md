# 志愿服务管理平台

FastAPI + SQLAlchemy（PostgreSQL）+ Redis + Vue3 / Element Plus / ECharts（Vite 构建）。
覆盖「活动发布 → 青协审批 → 报名（即选即得 / 报名后筛选）→ 候补流转 → 一键分配 →
扫码签到签退 → 时长核准与锁定」全链路。

## 一、快速启动

统一用 Docker 跑（后端依赖 PostgreSQL 与 Redis 两个服务，不支持本机直跑）。
`docker-compose.yml` 是公共部分，**三种形态各配一份叠加文件**，用 `-f` 组合：

| 形态 | 叠加文件 | 起的服务 | 访问方式 |
|---|---|---|---|
| **本机调试** | `docker-compose.local.yml` | postgres + redis + migrate + backend + web + backup | http://localhost:8080 |
| **内测** | `docker-compose.intranet.yml` | 上面这些 **+ caddy + cloudflared** | https://<域名>（caddy 终止 TLS；隧道兜公网） |
| **生产** | `docker-compose.school-db.yml` + `docker-compose.prod.yml` | redis + migrate + backend + web + backup（**无本机 postgres、无 caddy、无隧道**） | https://volunteer.ruc.edu.cn（nginx 用学校证书终止 TLS） |

```bash
cp .env.example .env          # 填 POSTGRES_PASSWORD、YVRUC_ID_CARD_KEY

# 本机调试（日常开发，http 直连）
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build

# 内测（本机当服务器；另需 cp caddy.env.example caddy.env 填域名与 Cloudflare 令牌）
docker compose -f docker-compose.yml -f docker-compose.intranet.yml up -d --build

# 生产（学校虚机；另需把学校证书放成 .certs/{fullchain,privkey}.pem）
docker compose -f docker-compose.yml -f docker-compose.school-db.yml -f docker-compose.prod.yml up -d --build

docker compose --profile seed run --rm seed     # 清空数据库并导入演示数据（只在开发机上用）
docker compose --profile test run --rm tests    # 跑回归测试（独立的 yvruc_test 库）
```

- 三种形态都往同一个 web 容器里落（nginx）；区别只在**谁终止 TLS、证书从哪来**：
  - 本机调试：没有 TLS，nginx 直接监听 80 映射到宿主机端口，http 访问
  - 内测：`caddy` 在宿主机 80/443 终止 TLS（证书用 Let's Encrypt 的 DNS-01 签，见
    「内网 https 与证书」）；cloudflared 隧道是公网那条路，TLS 在 Cloudflare 边缘终止
  - 生产：**nginx 自己**监听 443、用学校发的证书终止 TLS，前面没有 caddy、没有隧道
- 每种形态的配置项都写在各自叠加文件的头部注释里；`.env` 里的
  `COMPOSE_FILE` 也能固定形态（**Windows 用分号分隔、Linux/macOS 用冒号**），
  三种换着用时建议不用它、直接 `-f` 写清楚。
- 平台域名写两处：`.env` 的 `YVRUC_PUBLIC_BASE_URL`（二维码与通知链接用它）和
  内测时 `caddy.env` 的 `YVRUC_DOMAIN`（caddy 按它签证书），两个填同一个。
- 前端 8080 / 数据库 5433 / Redis 6380 / 后端 8000 都只绑 `127.0.0.1`，调试用得上、
  局域网和公网都连不上（本机调试形态的 8080 会放开到局域网，方便手机连同一个 wifi 测签到）。
- `caddy.env` 不存在时 compose 照常加载（CI 上就没有），只是 caddy 起不来。
- `docker logs yvruc-caddy` 看证书签发，`docker logs yvruc-cloudflared` 看隧道状态。
- **用户上传的文件全在一个命名卷 `yvruc_files` 里**（挂在容器的 `/app/data/files`）：
  学习材料、立项书与结项书、模板、报名问卷附件、反馈截图、时长补登的证明与照片、
  活动联络群二维码。谁能看由各接口自己的鉴权决定，和目录无关，所以不按「材料 / 二维码」
  分两个卷。数据库存 `yvruc_pgdata`，天地图瓦片缓存存 `yvruc_tiles`，操作日志存
  `yvruc_oplog`，caddy 的证书与账户密钥存 `yvruc_caddy_data`。
- 启动时 Redis 与身份证加密密钥都是**硬依赖**：连不上、密钥不对直接起不来——
  半可用的服务比起不来更难排查。数据库的迁移版本不是代码里最新的那一版，后端也拒绝
  启动，见下面「数据库迁移」。
- **证书与私钥不进仓库**：`.certs/`（生产用学校证书）与 `caddy.env`（内测的
  Cloudflare 令牌）都已在 `.gitignore` 里，误提交后先吊销令牌再清历史。


### 数据库迁移（Alembic）

表结构只由迁移建、只由迁移改，迁移文件在 `backend/migrations/versions/`。
`docker compose up` 时先起一次性的 `migrate` 服务（`python -m backend.migrate`）把库升到
最新，成功后才起 backend。后端启动只核对库的版本，不改表。seed 和回归测试也走同一套迁移建表。

**改了模型（`backend/models.py`），同一个提交里必须带上迁移**：

1. 起一个空库，或用开发库（`docker compose up -d postgres` 后先 `docker compose run --rm migrate`，
   让库停在改模型之前的那一版）。
2. 生成迁移：
   ```bash
   docker compose run --rm --entrypoint alembic -v ./backend:/app/backend migrate \
     -c backend/alembic.ini revision --autogenerate -m "一句话说明"
   ```
   本机装了依赖、`YVRUC_DATABASE_URL` 指着库时，直接 `alembic -c backend/alembic.ini revision --autogenerate -m "…"`。
3. **逐行检查生成的文件**。自动生成认不出改名（会写成删一列再加一列，数据就丢了），
   要手工改成 `op.alter_column(..., new_column_name=...)`；新加的非空列要给老数据一个值
   （先加可空列、`op.execute` 回填、再改非空）；需要搬数据的写 `op.execute`。
4. 跑全量 pytest。`tests/test_migrations.py` 会比对迁移后的库与模型，有一处对不上就红。

两个人各自基于同一版写了迁移、都合进 main，会出现两个 head，后端和迁移都会报错。
这时用 `alembic -c backend/alembic.ini merge heads -m "合并"` 写一条合并迁移。

**发版升级步骤**（库里有真实数据之后）：

1. 备份：`docker compose run --rm backup now`（见「备份与恢复」）。
2. 拉代码：`git pull`。
3. 重建并启动：`docker compose up -d --build`。`migrate` 先跑完迁移，backend 再起来；
   迁移失败时 backend 不会启动，看 `docker logs yvruc-migrate`。
4. 确认：`docker compose run --rm --entrypoint alembic migrate -c backend/alembic.ini current`
   显示的版本带 `(head)`。

生产库上不跑 seed：它会清空整个库。

### 连外部数据库

生产环境连学校统一数据库（PostgreSQL），不起本地 postgres 容器：

1. `.env` 里填 `YVRUC_DATABASE_URL`，例如
   `postgresql+psycopg://用户:口令@主机:5432/库名?sslmode=require`。问号后面的连接参数
   原样交给驱动（`sslmode`、`sslrootcert` 等）；口令里的特殊字符写成 URL 编码（`@` 写 `%40`）。
   要用证书文件时，把文件挂进 backend 和 migrate 容器，`sslrootcert` 写容器里的路径。
2. 启动时叠加 `docker-compose.school-db.yml`（它负责不起、也不等本地 postgres 容器）：
   生产形态用
   `docker compose -f docker-compose.yml -f docker-compose.school-db.yml -f docker-compose.prod.yml up -d --build`；
   在开发机上只想用学校库、其余照旧时，把 `docker-compose.prod.yml` 换成
   `docker-compose.local.yml`。写进 `.env` 的 `COMPOSE_FILE` 也行——**Windows 用分号
   分隔、Linux/macOS 用冒号**，写错了 compose 会把整串当成一个文件名。
3. `migrate` 会在学校的库里建表。所用账号要有建表、改表的权限（见《信息技术中心统一
   数据库管理规范》：账户默认只有普通用户权限，需要建表权限要先跟中心对齐）。

不填 `YVRUC_DATABASE_URL` 时连 compose 里的 postgres 容器，口令取 `POSTGRES_PASSWORD`。

### 内网 https 与证书（caddy）

caddy 用 Let's Encrypt 的 **DNS-01** 挑战签证书：靠往 DNS 写一条 TXT 记录证明域名
所有权，**不需要 80/443 从公网可达**，所以域名的 A 记录指向内网 IP 也照样能签下来。
签发与续期全自动（90 天一轮，到期前 30 天自己续），不需要人工介入。

- 需要 `caddy.env` 里的 `CF_API_TOKEN`：Cloudflare 令牌，权限 **Zone → DNS → Edit**，
  范围覆盖该域名所在的 zone。`caddy.env` 由 `caddy.env.example` 复制而来，**是本机
  文件、已被忽略，永不入库**——这个令牌能改你的 DNS，提交上去等于把它交出去；
  一旦误提交，先把令牌吊销重发，再改历史。
- 域名在 Cloudflare 里的 A 记录必须是 **DNS only（灰云）**：开橙云的话 Cloudflare 会
  尝试回源到那个内网 IP，整个域名就挂了。
- 镜像里的 Caddy 必须带 Cloudflare DNS 插件：官方 `caddy` 镜像没有，会报
  `unknown directive: dns`。所以用 `caddybuilds/caddy-cloudflare`（同一作者的
  `ghcr.io` 那份已经拉不到，registry 返回 denied；Docker Hub 这份正常）。
- 镜像用 `latest`，重建时跟着镜像作者的最新版本走。镜像里 Caddy 与插件的组合
  一旦对不上，会在装配 TLS 时 panic，报 `expected ModuleMap because inline_key is empty`
  ——这句话完全不指向版本，会让人去查配置（v2.9/v2.10 配插件 v0.2.x 就是这样）。
  撞上就换回已知能用的标签（如 `:2.11.7`），并确认证书还能签下来。
- 证书落在命名卷 `yvruc_caddy_data`，**别随手 `down -v`**：卷一删就重新签发，
  而 Let's Encrypt 对同一注册域限每周 50 张，调试期间重建几次会被锁一周。
  真要反复试配置，先在 Caddyfile 顶部加 `{ local_certs }`（浏览器会报证书不受信任，
  属正常），调掉后删掉再 `docker compose restart caddy`。

### 生产 https 与证书（学校证书，不用 caddy）

生产形态下 **nginx 自己监听 443、用学校发的证书终止 TLS**，前面没有 caddy——证书是
学校签好的，不需要自动签发那一套，少一个容器、少一跳，客户端 IP 也不用再从
`X-Forwarded-For` 里还原（nginx 直接看到浏览器地址）。
配置是 `web/nginx-https.conf.template`，由 `docker-compose.prod.yml` 连同证书目录挂进 web 容器，
顶掉镜像默认那份（内测与 CI 用的 http 80）。

- 证书放成两个文件，由 `YVRUC_CERTS_DIR`（默认仓库下 `./.certs`）挂进 web 容器的
  `/etc/nginx/certs`：
  - `fullchain.pem` 站点证书 + 中间证书（学校发的 `server.cer` 本身就是完整链，
    改名即可；`grep -c 'BEGIN CERTIFICATE'` 数一下有几张，≥2 才算完整）
  - `privkey.pem` 私钥，权限 `600`
- **换证书＝替换这两个文件 + `docker exec yvruc-web nginx -s reload`**，配置一行不用改。
  记下证书到期日，到期前换；过期当天浏览器会直接拦下整个站点。
- 证书里写的是哪个域名，访问就必须用哪个域名。学校发的是 `*.ruc.edu.cn` 通配符证书，
  覆盖 `volunteer.ruc.edu.cn`（**只覆盖一级子域**，`a.b.ruc.edu.cn` 不在内）。
- 没有 caddy 就没有 `http → https` 跳转（本形态不开 80 端口），浏览器与 HSTS 会自己
  走到 https；确需 80 跳转时再给 nginx 加一个 `listen 80` 的 server 并申请放行。
- 验证换证书是否生效（把域名换成实际的）：
  ```bash
  curl -sS -o /dev/null -w '%{http_code} TLS=%{ssl_verify_result}\n' https://volunteer.ruc.edu.cn/
  # TLS=0 表示证书链校验通过
  ```

### 环境变量（.env）

| 变量 | 说明 |
|---|---|
| `POSTGRES_PASSWORD` | 本地 postgres 容器的口令，用这个容器时必填；公网部署务必改掉示例值 |
| `YVRUC_DATABASE_URL` | 外部数据库的完整连接串，留空 = 连本地 postgres 容器。见「连外部数据库」 |
| `YVRUC_CERTS_DIR` | 生产形态的证书目录（默认 `./.certs`），挂进 web 容器的 `/etc/nginx/certs`。见「生产 https 与证书」 |
| `YVRUC_ID_CARD_KEY` | 身份证号的加密密钥，必填。**必须与数据库分开保管**，否则加密只是走过场；换密钥等于已有数据读不出来（先解密导出再重新写入） |
| `YVRUC_DEMO_PASSWORD` | 内测登录共享口令。**留空则整个演示登录接口不存在**；SSO 接通后必须留空 |
| `YVRUC_BOOTSTRAP_ADMINS` | 初始管理员的学号（教工号），逗号分隔。列在这里的人每次经统一身份认证登录，缺管理员身份就补上（原有身份保留，记一条审计），空库上线时用它指定第一个管理员；演示登录不受影响。**要撤掉其中某人的管理员，先从这里删掉学号再到「角色」页撤，否则下次登录会被补回**。留空 = 不启用 |
| `YVRUC_SSO_ENABLED` | 统一身份认证登录：`1` 走真实接口，留空或 `0` 走演示模式。开了却缺参数，后端拒绝启动并写明缺哪一项 |
| `YVRUC_MSGCENTER_ENABLED` | 消息中心推送：`1` 经学校消息中心下发，留空或 `0` 只落站内消息。开了要填齐开放平台的 appid、secret、网关 |
| `YVRUC_OPENPLATFORM_APPID` / `_SECRET` / `_GATEWAY` | 学校开放平台的应用标识、密钥、网关，在应用中心注册应用后获得 |
| `YVRUC_CAS_BASE_URL` | 统一身份认证根地址，OAuth 三个端点按它拼 |
| `YVRUC_SSO_AUTHORIZE_URL` / `_TOKEN_URL` / `_USER_INFO_URL` | 单独指定 OAuth 端点，留空按 `YVRUC_CAS_BASE_URL` 拼 |
| `YVRUC_SSO_CLIENT_ID` / `_CLIENT_SECRET` | OAuth 的 client_id / secret，留空用开放平台的 appid / secret |
| `YVRUC_SSO_REDIRECT_URI` | OAuth 回调地址，必须与应用中心登记的一字不差 |
| `YVRUC_MSGCENTER_CHANNELS` | 推送通道，`2` 邮件、`4` 企业微信，逗号分隔，默认 `4`。填 `1`（短信）后端拒绝启动 |
| `YVRUC_PUBLIC_BASE_URL` | 平台对外网址（多个用逗号分隔）。二维码里写的就是它，只有列在这里的域名才允许出现在码里。与 `caddy.env` 的 `YVRUC_DOMAIN` 填同一个 |
| `YVRUC_EXPOSE_DOCS` | 设为 `1` 才暴露 `/docs` 与 `/openapi.json`，默认关闭 |
| `YVRUC_TIANDITU_TK_SERVER` | 天地图**服务端** tk：管理端地图瓦片转发 + 地名搜索。要在天地图后台登记服务器公网出口 IP；只在后端用，不进前端。留空 = 地图只显示点和圈 |
| `YVRUC_TIANDITU_DAILY_LIMIT` | 每天向天地图取瓦片的上限，默认 10000（天地图给的额度），到上限直接 503 |
| `YVRUC_AI_API_KEY` | 智能起草（活动管理右下角的按钮）用的 key，留空则按钮不出现。贴进去的原文、上传的附件会发给这家服务 |
| `YVRUC_AI_BASE_URL` / `YVRUC_AI_MODEL` | OpenAI 兼容接口的地址与模型，默认 `https://api.deepseek.com` / `deepseek-flash`（附件里的图片要模型能识图） |
| `YVRUC_AI_TIMEOUT` | 一次起草最多等几秒，默认 90 |
| `YVRUC_AI_THINKING` | 思考模式 `enabled` / `disabled`，默认 `disabled`；服务商不认这个参数时填 `none` |
| `YVRUC_SENTRY_DSN` | 错误监控的 DSN（见「错误监控」），形如 `http://<公钥>@glitchtip:8000/1`。**留空 = 完全不上报**，SDK 都不初始化；填得不成样子则后端拒绝启动 |
| `YVRUC_SENTRY_ENVIRONMENT` | 环境名，监控服务上按它分开生产与内测的事件，默认 `production` |
| `YVRUC_SENTRY_SAMPLE_RATE` | 错误事件的采样率 `0`～`1`，默认 `1`。填成 `10`、`100` 这种百分比写法后端拒绝启动 |
| `YVRUC_SENTRY_TRACES_SAMPLE_RATE` | 性能追踪的采样率 `0`～`1`，默认 `0` 不报（追踪是每个请求一条，自建的轻量服务存不住） |
| `YVRUC_SENTRY_ALERT_THRESHOLD` | 同一个错误 10 分钟内到多少次就给全体管理员推一条站内通知（每个错误每天至多一条），默认 `20`，`0` = 不推 |
| `CLOUDFLARE_TOKEN` | 隧道令牌，勿提交/外传。留空 = 隧道容器起不来，内网 https 入口不受影响 |
| `YVRUC_BACKUP_DIR` | 备份写到宿主机的哪个文件夹，默认仓库下 `./backups`。Windows 写 `D:/yvruc-backups` 这样的正斜杠路径 |
| `YVRUC_BACKUP_AT` | 每天几点备份，默认 `03:00` |
| `YVRUC_BACKUP_DB` | 设为 `0` 不导出数据库、只备文件卷（数据库由别处备份时用），默认 `1` |
| `APK_MIRROR` | 备份容器构建时装系统包用的 Alpine 镜像站，默认清华镜像。服务器在境外时改成官方源 `https://dl-cdn.alpinelinux.org/alpine` |
| `HTTPS_/WEB_/BACKEND_/POSTGRES_/REDIS_HOST_PORT` | 宿主机端口，被别的项目占用时改这里 |

### 登录方式

学校统一身份认证（微人大，走 CAS 服务器上的 OAuth2.0 接口）是唯一正式入口，
开关和参数在 `.env`（见上表 `YVRUC_SSO_*`），改完执行 `docker compose up -d` 生效。
接通之前，开发小组用 `POST /api/auth/demo-login`（学号 + `YVRUC_DEMO_PASSWORD` 共享口令）
登录；口令连错 10 次锁该来源 IP 5 分钟。`GET /api/auth/sso-mode` 会如实告诉前端当前是
哪种情形（演示登录 / SSO 已接通 / 两者都没有、谁也进不来）。

会话 3 天不用即过期（每次使用都往后顺延），令牌只认 `Authorization` 头，**唯一的例外是导出与材料下载**这一个直链
场景：前端先换一张票据（绑那一个网址、60 秒有效），地址栏里因此
永远不会有会话令牌。

### 备份与恢复（`backup/`）

compose 里的 `backup` 服务随 `up -d` 一起起来，每天 3:00 备一份，写到宿主机的普通文件夹
（`.env` 的 `YVRUC_BACKUP_DIR`，默认仓库下 `./backups`，已被 git 忽略），资源管理器里直接
能看到、拷走。电脑在 3:00 关着机的话，开机后当天补一份。

- **备什么**：数据库（`pg_dump`，服务不用停）和两个文件卷：`yvruc_files`（用户上传的
  文件：材料、立项书结项书、反馈截图、二维码等）、`yvruc_oplog`（操作日志）。
  不备天地图瓦片缓存、Redis、caddy 证书，它们丢了能重建。
- **每份备份**是一个文件夹，名字形如 `2026-10-12_0300_daily`，里面是 `db.dump`、
  `files.tar.gz`、`oplog.tar.gz` 和 `manifest.json`。`files.tar.gz` 里装的是
  用户上传的全部文件——包括二维码，它们和材料同卷。
- **留多久**：定时备份留最近 7 天，每周再留一份（这一周最后一份，一般是周日），留 4 周；
  每月再留一份（这个月最后一份），留 6 个月。手动备份另算，留最近 10 份。
- **只存本机**：防误删、防重建库，防不了硬盘坏。要防硬盘坏，把 `YVRUC_BACKUP_DIR` 设到
  另一块盘上，或者定期把这个文件夹拷走。
- **身份证加密密钥不在备份里**：`YVRUC_ID_CARD_KEY` 只在 `.env`。备份里的身份证号是加密的，
  密钥丢了恢复出来也读不出。把密钥单独存一份（密码管理器或打印出来），不要和备份放在一起。
- **数据库不归我们备时**（例如连学校统一数据库）：`.env` 设 `YVRUC_BACKUP_DB=0`，只备文件卷。
  完全不要了就删掉 compose 里的 `backup` 服务。导数据库时连的是 `YVRUC_DATABASE_URL`，
  和 backend 同一个库；连接串里用到证书文件的话，`backup` 容器也要挂上。
- 备份文件夹在 Windows 上的写法：`.env` 里写 `YVRUC_BACKUP_DIR=D:/yvruc-backups`
  （正斜杠；Docker Desktop 设置里的 File sharing 要包含这个盘）。改完 `docker compose up -d backup`。
- Linux 上先用部署账号建好这个文件夹（`mkdir -p /srv/yvruc-backups`）：备份交给文件夹的属主，
  只有属主能读。让 Docker 自动建的话属主是 root，要 sudo 才打得开。

```bash
docker compose run --rm backup now    # 立即备一份：部署、重建库、改表之前都跑
docker compose run --rm backup list   # 列出现有备份
docker logs yvruc-backup --tail 20    # 看每天的备份有没有成功
```

**恢复**（会覆盖现在的数据，备份之后的改动全部丢失）：

```bash
docker compose run --rm backup now                    # 先把现在的状态也备一份，以防选错
docker compose stop backend                           # 恢复数据库时不能有别的连接
docker compose run --rm backup restore 2026-10-12_0300_daily --yes
docker compose up -d                                  # migrate 先把恢复出来的库升到当前版本，backend 再起来
```

- 只恢复其中一样：加 `--only db` 或 `--only files`。
- 恢复到一个全新的库（换电脑、`down -v` 之后）：先 `docker compose up -d --wait postgres`
  （`--wait` 等数据库能连上才返回），再跑上面的 `restore`，最后 `docker compose up -d`。
  `.env` 里的 `POSTGRES_PASSWORD` 与 `YVRUC_ID_CARD_KEY` 要和原来的一样。
- 备份比现在的代码旧时，恢复出来的库停在旧的迁移版本，`up -d` 时由 `migrate` 升上来。
- 文件卷恢复时先清空再解包，备份之后新增的上传件会被删掉。

### 错误监控（自建 GlitchTip，`backend/monitoring.py`）

后端没接住的异常报到自建的监控服务：按「同一个错误」归并，页面上能看堆栈、第一次与
最近一次、出现了多少回。`ERROR` 及以上的日志也成为事件（`logger.exception` 写在哪里，
监控上就看得到哪里）。**不配 `YVRUC_SENTRY_DSN` 就完全不启用**，本机调试、CI 和测试里
天然是关着的。

服务端用 GlitchTip（Sentry 协议的轻量实现，约 512MB 内存；Sentry 官方自托管要 4 核
16GB 起步）。它的编排是单独一份 `ops/docker-compose.monitoring.yml`，不并进平台那套：
重启平台不会把监控一起停，监控挂了也不影响报名。它自带一个 PostgreSQL 容器——生产形态
的平台连的是学校统一数据库，那个账户没有导出权限、建表还要另外对齐，而监控的事件表是
纯运维流水，不该进学校的库。

**起服务**（在仓库根目录；平台那套要先起着，监控容器要挂进它的网络）：

```bash
cp ops/monitoring.env.example ops/monitoring.env   # 填两个随机串：库口令与 SECRET_KEY
docker network ls | grep default                   # 确认平台网络名（默认 yvruc_system_default）
alias m='docker compose --env-file ops/monitoring.env -f ops/docker-compose.monitoring.yml'
m up -d
m logs -f glitchtip                                # 迁移自己会跑，起来约半分钟
```

**看页面、拿 DSN**：页面只绑在服务器本机的 8001 端口（生产入向只放行 443，监控不该
暴露在公网），从自己电脑上开一条隧道看：

```bash
ssh -L 8001:127.0.0.1:8001 <用户>@<服务器>   # 然后浏览器开 http://127.0.0.1:8001
```

1. 第一次打开先注册——**自助注册在第一个人注册后自动关闭**，所以装好就去注册，别留着。
2. 建一个组织和一个项目（项目平台类型选 Python / FastAPI 都可以，它只影响页面上的提示）。
3. 在项目设置里复制 DSN，把主机名换成容器里的地址：
   `http://<公钥>@glitchtip:8000/<项目号>`（后端走 compose 网络找它，用的是服务名，
   不是 127.0.0.1——那样后端只会连到自己）。
4. 填进 `.env` 的 `YVRUC_SENTRY_DSN`，`docker compose up -d` 重启后端。
   启动日志里会有一行「错误监控已启用」；DSN 填得不成样子时后端直接拒绝启动。

**上报了什么、没报什么**。排查时要知道自己看不到什么：

| 报 | 不报 |
|---|---|
| 异常类型与消息、堆栈、出错的接口、环境名、主机名 | 请求正文（报名问卷答案、个人资料） |
| 请求的方法与路径（查询串已截掉） | Cookie、`Authorization`、下载票据与瓦片令牌 |
| `User-Agent`、`Content-Type`、语言、来源页 | 其余请求头 |
| | 堆栈帧里的局部变量 |
| | 用户身份（谁触发的去「操作日志」页按时间和路径对） |

剩下的文字（异常消息、日志、面包屑、网址）还会按正则盖掉身份证号、手机号、`Bearer`
令牌和 `token=` / `ticket=` 这类参数值。脱敏自己出错时整条事件丢掉——少看到一个错误，
比漏出一个身份证号轻得多。

**同一个错误刷屏时**（10 分钟内到 `YVRUC_SENTRY_ALERT_THRESHOLD` 次，默认 20），给全体
管理员推一条站内通知，每个错误每天至多一条。通知由后台定时任务发，上报的那一刻只在
Redis 上记一次数：错误风暴多半就是数据库出了问题，那时候逐条去查管理员名单只会雪上
加霜。

**升级与留存**：`m pull && m up -d`，数据库迁移自己跑；镜像钉的是大版本标签，大版本
一年一次、可能有破坏性变更，升级前看一眼 <https://glitchtip.com/blog>。事件默认留
90 天（`GLITCHTIP_RETENTION_DAYS`）。监控的数据不进平台的备份，丢了就丢了——它是排查
线索，不是业务数据。

## 二、权限体系

权限是三层叠加的，各管一段：

| 层 | 载体 | 说明 |
|---|---|---|
| 身份 | `User.roles`，可多个 | `admin` 管理员 / `qingxie` 青协 / `initiator` 活动发起方 / `student` 学生。顶栏切换视角；路由守卫在视角不够但持有对应身份时自动切换放行 |
| 类型 | `User.user_type`，二选一 | `teacher` / `student`。**老师类型不参与志愿报名**（自主报名与管理员补录均拦截），也不用补充个人信息；老师首次登录即自动获得 `initiator` 活动发起方身份，学生获得 `student` |
| 青协层级 | `User.qingxie_post` | `council` 会长团（除平台公告、操作日志、意见反馈外与管理员同权）/ `head` 部长 / `core` 部门骨干 / `member` 部门成员 |
| 活动级 | `activity_managers` | 谁能看、能操作哪个活动（见下） |

**部门成员是「学习权限」**：平时就是来报名的学生，切到青协视角能进工作台、能看，
但**任何写请求都在依赖层被拦**（试算类接口除外，导出也禁）。拦在依赖里而不是各个接口里，
是因为管理端写接口有五十多个，逐个加判断必然漏。

| 页面 | 可见身份 |
|---|---|
| 数据总览 dashboard | 管理员、会长团 |
| 平台公告 announcement | 仅管理员 |
| 操作日志 oplogs | 仅管理员（会长团也不行） |
| 志愿者档案 users | 管理员、会长团、部长 |
| 活动审批 approvals | 管理员、会长团、部长；对外联络部的部门骨干（有值班资格） |
| 角色管理 roles | 管理员、会长团、部长；部门骨干进来只为认领本部门成员 |
| 活动管理 manage | 管理员 / 活动发起方 / 青协 三个视角 |
| 审计日志 audit | 同上；管理员与会长团看全部，其余只看自己管理的活动 |
| 个人页（广场 / 我的报名 / 时长） | 仅学生视角；工作台视角下打开时，持有学生身份就自动切到学生视角，没有才跳回活动管理（消息中心两种视角都能进） |

活动多人共管（`activity_managers`）：创建者自动成为管理者且**不可被移除**；管理者之间
权限完全相同、可互相添加/移除，但**不能移除自己**；被添加者必须持有活动发起方/青协身份；
管理员无需添加、天然可见全部。部长另外能看到本归口部门的全部活动；部门成员看到的范围
**跟着自己归属的那位骨干**——成员是跟着某个人学做事的，不是跟着整个部门。

### 对外联络部：值班、志愿北京外联确认、立项书与结项书（`backend/liaison.py`）

二级志愿团体的活动都归口对外联络部，审批量远超其他部门，所以只在这个部门（按部门名认）启用值班；
其他部门的审批行为不变。

- **值班**：同一时间一人，只能是本部门的**部门骨干或部长**。部长（及会长团、管理员）在「活动审批」
  页指定或撤下；在班的人自己交给另一位骨干/部长。交接留流水（谁、从谁、交给谁、何时、备注）并写审计。
  值班人被调离部门或降为成员，值班自动失效。
- **审批路由**：提交/转交到对外联络部、时长锁定与解锁申请、志愿北京外联确认、审批超时催办，通知**只发值班人**
  （没人值班才发部长）。审批人仍挂部长，值班人与部长都能处理本部门
  的活动审批（通过/驳回/转交）与时长审批；转给会长团之后部门不再插手。
- **时长审批通知**（所有部门）：锁定与解锁申请逐条**只发归口部门的对接人**（有值班人发值班人，
  否则部长），不逐条抄送会长团与管理员——他们照样能在「活动审批」处理。找不到对接人（部门没设
  部长）才兜底发会长团。提交后 48 小时（`APPROVAL_REMIND_HOURS`）仍未处理，催对接人并抄送负责该部门的会长团，
  每条只催一次（`HoursRequest.reminded_at`）；永不自动通过。
- **值班日报与交接提醒**：每晚 21:00 给部长一条当天汇总（今日新增 / 今日处理 / 尚未处理，含志愿北京外联确认），
  三栏都空不发；用一条条件更新占下当天日期，清扫多轮、换主、重启都只发一次。交接提醒按接班那天算：接班是周几，之后每周那天 21:00 提醒当前值班人处理未完成的待办并完成交接班，第一次落在接班后第 8 天；查不到交接记录的部门按周日提醒（`Department.duty_remind_on`）。
- **志愿北京外联确认**（**所有活动**，不论归口哪个部门）：管理者提交时长审核时一并填志愿北京上的
  活动名称（可填多个，至少一个；「审核」页签里也能先存）。时长审核通过、锁定后，活动落「待外联确认」
  （`vb_pending`），名称推给对外联络部**值班人**（没人值班发部长，都找不到兜底会长团）。外联（值班人、
  部长、会长团、管理员）上志愿北京核对后在「活动审批」或「审核」页签**确认**（意见选填）→ 活动
  「已完成」；或**退回**（理由必填）→ 通知管理者，管理者在「审核」页签改名称**重提**（只重提名称，
  时长保持锁定，不重走时长审核）→ 外联再收到。每次推送/确认/退回都留在 `VbConfirm` 上并写审计，
  审核页签里能看到全部往来。
  - 推送超过 48 小时（`APPROVAL_REMIND_HOURS`）没人处理，催外联对接人**一次**（`VbConfirm.reminded_at`）；
    被退回满 3 天（`VB_REMIND_DAYS`）管理者还没重提，每天 9 点起提醒管理者一次（`Activity.vb_reminded_on`）。
  - 时长解锁不动外联确认：志愿北京上录的只是活动名称，时长改了不必外联重核。重新锁定时名称没变的，
    已确认的直接回到「已完成」，待确认、已退回的照旧等外联确认或管理者重提；名称变了才作废旧的待确认、重推一条。
- **立项书 / 盖章立项书 / 盖章结项书**：活动管理「审核」页签，只有活动管理者能传，每格只留一份
  （传新即替换，旧文件删除，上传写审计），下载只给管理者与审批线上的人（值班人、部长、会长团、管理员）。
  - 立项书（docx、pdf）：**提交对外联络部审批必须有**，「提交审批」对话框里就能传；审批中可以换，
    通过后不能再换；**被驳回即作废**（连文件删掉），重新提交要传新的一份。转进对外联络部却没有立项书的，
    不能通过。
  - 盖章立项书（即盖章项目申请书）、盖章结项书（即盖章时长认证明细）（pdf 或图片，多页合成一个 PDF）：只用于对外活动（归口对外联络部），时长
    锁定前随时可换（审核中、已锁定不能换），「提交时长审核」对话框里也能传。**手动提交时长审核两份都
    必须有**；申诉期满的自动提交遇到缺了就不提交，只提醒管理者一次，补传后下一轮清扫照常提交。审批人
    在「活动审批」的时长审批卡片上直接下载这两份。
- **模板**：立项书、结项书的空白模板（docx）由外联部长（及会长团、管理员）在「活动审批」页上传和
  更换，每种只留一份；发起方在「活动管理」页的「材料模板」下载，传立项书、盖章材料的地方也有下载链接。

## 三、岗位模型（场次 → 岗位）

结构：Activity ─ Shift（场次：起止时间）─ Position（岗位：职责、名额、条件）。

- **时间只存在于场次这一层**，岗位没有自己的时间。场次是时段冲突检测的单位，
  同场次内的岗位互斥（一人一场次只占一个岗位），所以换岗不会产生新的时段冲突。
- 场次两种模式：`pick` 报名即选岗位（运动会）；`assign` 报名只锁时段，截止后由
  一键分配统一分工位（图书整理周）。`assign` 场次建场时自动带一个**占位岗位**装
  「还没安排的人」，一键分配只往真实岗位里排，排不下的自然留在占位岗位里。
- 培训 / 彩排也是场次，只是**附属**于某个服务场次（`parent_id`）：报名主场次时连带
  报上、退选时连带退，自己不设名额。这样签到码、到岗大屏、时长计算、冲突检测全部
  原样复用。附属场次可以指定只对某几个岗位生效（东门组周五彩排、检录组周六彩排）。
- 条件要求按标签匹配志愿者档案，可选标签就五个：性别 / 学院 / 年级 / 校区 / 学段。
  场次与岗位各能设一套（`requirement_tags`），报名时直接拦截，一键分配时同样作为硬约束；
  活动层另有「招募范围」限定校区、学段与学院，整个活动一刀切：范围外的人广场上看不到、
  转发来的链接打开提示原因、报名被拦；已报名/申请的人不受影响（缩小范围时先列出名单，
  管理者明确保留才改）。学院取值是统一身份认证的原文，可选项由
  `GET /api/staff/colleges` 从已有用户档案汇总（并上 `config.COLLEGES` 兜底），不卡固定清单，
  岗位/场次条件里的学院也用这份选项。**认识不了的标签不拦人**——
  一个错别字不该把所有人挡在外面。岗位另外有三段给志愿者看的文字
  （服务任务 / 岗位要求 / 培训内容）与服装、报酬说明。
- 同一场次里组名相同的岗位共用一名组长。

## 四、报名 / 候补 / 名额

- 招募模式两种：`instant` 即选即得（名额满自动进候补）/ `screened` 报名后筛选
  （填报名问卷、勾意向岗位，报名截止后由管理者录取：名单上每人一行，勾选录到他意向里的
  哪几场、选岗位的场次可改岗位，逐人录取或勾选几人一起录，**逐人各自成败**——名额不够、
  时间冲突只拦那一个人，结果逐人列出）。
  意向场次开始时仍未处理的，该场次的意向由定时任务自动作废；全部意向场次都已开始
  还没处理的申请自动落选，并发送与手动不录取相同的通知（晚开始的场次仍可录取）。
- 冲突检测**只比场次时间区间**，跨活动、也比本活动别的场次：与本人有效报名的区间重叠时
  **提示而不硬拦**——回 409（`detail.code = "time_conflict"`，附冲突明细），前端弹窗确认后
  带 `confirm_conflict: true` 重发即放行（名额照常判）。报名、申请、管理者录取、补招都这样；
  候补自动转正、一键分配这类没人可问的自动路径不查冲突。**候补中的场次同样算已占用
  时段**——排了队就等于预留了这段时间。
- 每个场次各自算截止：`min(活动报名截止, 本场次开始时间)`，开场即不收人。
- 名额只有岗位上这一个来源。已消耗 = `enrolled` + `pending_confirm`。
  容量判断与落库整段持场次锁串行化，配合 `enrollments` 的部分唯一索引，
  杜绝抢报瞬间的超卖与重复报名（见 `backend/locks.py`）。场次锁是 Postgres 的
  事务级咨询锁，拿在请求自己的会话上、随事务提交/回滚释放（没有租期，不会
  「活还没干完锁先过期」）；每个进程最多 `YVRUC_LOCK_SLOTS`（默认 5）个请求
  带着连接去数据库排队，其余在进程内等，不占连接池。前面再挡一道 Redis 名额闸门，
  抢不到号的请求一次 Redis 往返就回「满了」。
- 抢报压测：`scripts/rush_bench/`（300 人抢 200 名额 + 50 候补，另有 20 人刷页面），
  用法见其中 `run.sh` 开头。数字只做同一台机器上的前后对比。
- 满员进候补队列（按报名时间排序）。有人退选释放名额 → 队首转正 `pending_confirm`，
  开 **2 小时确认窗口**，夜间 23:00–8:00 不计时（22:30 转正 → 次日 9:30 截止），
  且不晚于场次开始（清扫协程 + 惰性判定双保险），超时记一次「放弃」并顺延下一位。
  名单锁定、报名暂停时候补不再自动顶上，要不要补人由管理者手动转正。场次开始后
  不再转正候补（自动、手动都不转），还在候补的人自动结束并收到「未能递补」通知，
  不算本人退出；开场后要补人用补招。
- **名单锁定**：场次开场前 `lock_hours` 小时自动锁定（默认 12，范围 0～72，
  0 = 不自动锁定），场次和单个岗位也可以随时手动锁定 / 解锁（不进编辑态，留痕）。
  锁定后不收新报名、新候补，候补不自动顶上，此时退出的志愿者记一次**「锁定后退出」**，
  扣 5 分并通知管理者。解锁时按候补顺序把空位补齐，报名没截止的同时重新收人。
- **暂停报名**（调整岗位用）：不收新报名、新候补，候补也不顶上，期间名单不动；
  已报的人可以退出，不记录。恢复时同样按候补顺序补齐空位。
- 报名时可勾选**是否接受岗位调剂**（`allow_reassign`），随时可改；候补与报名后筛选的申请
  也按本人勾的来（默认接受）。这只是给管理者的参考：名单、分配面板与导出表都会显示，
  管理者仍可调换工位，但违背本人意愿的调换会连同姓名写进留痕。
- **广场可以按时间范围筛**（与所选区间**有交集**的服务场次才算，跨天的活动沾到任一天就
  出现），配「今天 / 本周末 / 未来 7 天 / 未来 30 天」快捷项：志愿者按「这几天我有空」
  找活动。候选集先在 SQL 里按时间跨度与业务状态砍一刀，再按时间算展示状态。

**平台不对志愿者做任何限制**：没有准入名单，不拦任何人报名，也不冻结任何东西。
违规记录（迟到早退 / 无故请假 / 消极志愿 / 其他）只是归档，青协在志愿者档案里
看得到；「提示分」是给青协内部看的参考值，实时算出来，低于 80 只在名单上挂一个感叹号，
不产生任何后果。算法：100 分起，三项都按活动计——每条违规按类型扣分；一个活动里有锁定后退出
扣一次（退几个场次都只扣一次）；一个活动签到过（含管理者补签）、没有违规也没有锁定后退出，
等他报的场次都结束后加 5 分。所有加扣按时间顺序逐条累计，每一步都夹在 0～100 之间，
满分时加的分不会存起来抵后面的扣分；档案里按时间列出每一步。

## 五、签到签退与时长

- 同一签到码：**第一次扫=签到、第二次扫=签退**、已签已退再扫拒绝；仅本场次已报名
  （`enrolled`）的志愿者有效。任务两种：整场次一个统一码，或每个岗位一个独立码；
  可签时段默认取场次起止各外扩 30 分钟（提前到岗与拖堂散场都签得上）。
  二维码 SVG 直达落地页 `/checkin/{token}`；管理端实时大屏（前端 5s 轮询）
  显示到岗/离岗率。
- 签退没有另外的宽限：签到、签退都只在签到码的**可签时段内且码开着**时能自己做。
  这一场已经没有能用的码（过了截止，或被关掉/删掉）时还没签退的，由系统**按场次结束时间兜底**
  （auto 标记）；码还开着没过截止的记为时长待定（pending）。两类都标为**待核**，需管理者
  逐条核对数值后单独确认——到场扫个码就走的人会和全程服务的人算出一样的时长。
  兜底是每次现算的：关掉的码重新开、或把截止往后改，没签退的人又回到待定。截止必填，
  管理端把截止设得早于场次结束、或在场次结束前关码，都会先弹确认说明这个后果。
  管理者手动补签/签退不受码的时段限制。
- **时间灵活的场次**（`flexible_time`，长期招募、时间报名后协商）一张码一轮：每张签到码每人
  签一次到、一次退，同一张码签退后再扫拒绝，负责人开一张新码就能再签一轮；时长按各轮累加，
  每段写那一轮的实际起止。某一轮没签退的，按**那张码的截止时间**兜底并待核，能不能签退也只看
  那张码。管理者补签、手动签退落在当前开着的那张码上（没开码要先开）。这类场次时长只能
  `checkin` 或 `none`，不能 `fixed`。
- 时长认定按场次的 `hours_mode` 三选一：`checkin` 签退−签到 / `fixed` 到场即按场次时长 /
  `none` 只记出勤不算时长。把不确定性收在建场次这一次决定里，而不是散在事后逐条核对里。
- 时长 = 签退 − 签到，**向上取整至 0.5 小时**；按场次分段存明细，志愿者看得到自己的每一段。
- 结账是一条链，不是一次点击：**管理者核准**（通知本人）→ 本人于申诉截止
  （默认第二天中午）前确认或申诉 → 期满无人申诉由定时任务自动提交 → **归口部长审批锁定**
  （对外联络部由值班人处理，且要有盖章立项书和盖章结项书，见第二节），通过即锁定，
  活动落「待外联确认」（`vb_pending`）→ **对外联络部**在志愿北京核对管理者填的活动名称并确认，
  活动才落「已完成」；退回则管理者改名称重提（见第二节「志愿北京外联确认」）。
  - 提交时长审核**必须带至少一个志愿北京活动名称**（审核期间名称随时长冻结）。申诉期满的自动提交
    遇到还没填名称，就不提交、每轮核准只提醒管理者一次（同缺盖章材料），填好后下一轮照常提交。
  - 一条时长记录都没有的活动，核准即锁定并直接「已完成」：志愿北京那边没有可录的，不推外联。
  - **党校同学**只能经补招加进来（补招对话框勾「党校同学」）：时长带「党校」标签，不进「导出时长
    记录」、不计入本人累计时长（不能同时拿去做学分认定）；数据总览照算。
  - 时长审批（锁定/解锁）通过时意见选填、驳回必填，意见随通知发给申请人，审核页签的历史里看得到；
    活动立项与外联确认同样如此，前端共用一个审批意见对话框（`ApprovalCommentDialog`）。「通过」时有
    校青协定的常用语，点一下整段填进意见框（`web/src/replyTemplates.js`）：立项通过、结项通过
    （时长锁定）、志愿北京立项通过（外联确认，填的是志愿北京活动名称）。
  锁定后还要改，走解锁申请单，让部长知道改什么、为什么改；解锁通过一律回到「已结束」
  （不论此前是待外联确认还是已完成），外联确认不作废，重新锁定时按名称变没变处理（见「志愿北京外联确认」）。
  时长锁定与解锁申请可以由申请人本人审批，意见和审计前标「【本人审批】」。
  审批期间时长冻结，部长看到的和最终封的必须是同一份账。
- 岗位可以勾「可选劳务」：志愿者在确认时选劳务，平台就不给这个人记时长，导出到志愿北京
  的时长表里也不含他。
- 一笔时长的明细是 `hours_segments` 里的行，一段一行：签到结算按场次一段（`shift`）、
  管理者手动加/扣一段（`manual`，扣减记负数）、补记录活动导入名单一段（`import`）。
  每段记原始小时数与**服务日期** `date`，记录 / 活动 / 人三列都有索引，
  「按服务日期统计」一条 SQL 就能出，不必把明细拉进 Python 逐行拆。
- 每一笔的 `hours` 恒等于该笔各段之和（原始值）：由模型的 `before_flush` 钩子在一处
  重算（`_sync_hours_from_segments`），写段的路径再多也不会漏掉一处加法。
- 结算口径：一笔之内，志愿时长 = 非劳务段之和向上取整到 0.5，劳务 = 劳务段之和向上
  取整到 0.5，两者的和是结算合计（可能略大于原始合计，界面上有一行说明）。
  对外显示、导出、锁定、申诉都用它（`HoursRecord.split()` / `counted_hours()` /
  `pay_hours()`）。
- 定位签到的管理端小地图用天地图瓦片，**由本站服务器转发**（`backend/routers/geo.py`）：
  浏览器直连时浏览器端 tk 靠 Referer 域名白名单，AdGuard 隐身模式之类的插件会改掉
  第三方 Referer，天地图一律 403、地图整块灰掉。所以浏览器只请求
  `/api/geo/tiles/{vec|cva}/{z}/{x}/{y}?t=令牌`，拿不到任何 tk。
  - tk：只用服务端 tk（`YVRUC_TIANDITU_TK_SERVER`），**部署时要在天地图后台把服务器
    公网出口 IP 登记进白名单**；没配则地图只显示点和圈。浏览器端 tk 用不上：天地图对它
    只认真浏览器，服务器发出的请求带什么 Referer 都被拒（403 / 301012）。
    上游请求也**不能带浏览器样的 User-Agent**：天地图按 UA 分辨浏览器/服务器，带服务端
    tk 却用 Mozilla 开头的 UA 会被拒（403 / 301013）。
  - 额度（每个 tk 每天 10000 次）：同一张瓦片只向天地图取一次，磁盘缓存 30 天
    （`yvruc_tiles` 卷）；Redis 按天数真正打到天地图的请求（缓存命中不算），到九成记
    警告日志，到上限直接 503 不再请求上游；过期缓存在取不到新图时照旧拿出来用。
  - 防滥用：`<img>` 带不上登录令牌，所以管理者打开地图时先领一张瓦片令牌
    （`GET /api/geo/tile-token`，HMAC 签名、约 6 小时过期、不落库），前端快过期时自己
    重新领；瓦片接口先验令牌（缓存命中也验），无效或过期 401。

### 不公开招募（补记录）活动（`backend/routers/records.py`）

线下已经组织过、只需要在平台上补记时长的活动。建活动时「活动类型」选
**不公开招募（补记录）**（`recruit_mode="record"`，与即选即得、报名后筛选并列）。

- **只有基本信息**：名称、组织单位、地点、联系人、简介，外加**活动时间**
  （`held_start` / `held_end`——没有场次可算，直接填）。不要联络群、报名时间、招募范围、
  问卷；不能建场次岗位、不能发布、不能进编辑态。与招募活动之间只在草稿里互相切换。
- **不公开**：广场任何人都不列（含管理者自己），详情链接对非管理者、非审批线上的人 404，
  报名与申请一律被拦，学习材料同口径。
- **照常走立项审批**：提交归口部门、通过/驳回、对外联络部要立项书，规则不变。
  通过后**直接落「已结束」**（不发布），等管理者导入名单。
- **导入名单**（活动管理页「名单导入」）：粘贴文本或上传 `.xlsx` / `.csv`，每行
  「学号 时长 [备注]」，时长按小时、大于 0、0.5 精度，**不设上限**——超过 24 小时的
  照常导入，但在结果里标「超过 24 小时，请核对」。
  - **先预览、再确认**：粘贴或上传后先出预览，列出新增谁、覆盖谁（旧时长→新时长）、
    几人与名单一致不改动、跳过哪几行及原因、找不到的学号、超过 24 小时的人、会不会撤销
    已有核准；点「确认导入」才写入。确认时带上预览给的指纹，预览之后名单被别人改过
    （或交上来的内容变了）就不写，页面自动按最新名单重新预览；
  - 平台里**找不到的学号只列出来提醒，不建档**；
  - 同一批里重复的学号（取第一行并提示）、非法时长、老师类型，逐条给原因并跳过，
    其余照常导入；
  - 核准后新增、覆盖、改单人或删除名单，会撤销原核准和申诉截止时间；请到「时长管理」
    重新核准。重新核准只通知新增的、时长变了的和这一轮申诉过的人，其他人已经收到过
    同样的数，他们的确认照旧有效；
  - **再导一次即覆盖**（方便整批改）：新的人追加，已在名单里的人按这次的时长覆盖
    （记录与导入明细段一起改，本人之前的确认作废），结果单独列出「覆盖：姓名 学号
    旧时长→新时长」；这次没写备注的保留原备注，数值和备注都没变的不动。本人有**待处理的
    申诉时不覆盖**，列出来提醒先处理申诉。时长已锁定或已提交审核时，整批导入被拒；
  - 单人可改时长/备注、可删（提过申诉的不能删，改时长）；都在时长锁定之前。
  - 导入、修改、删除都记审计（动作「名单导入」），按人记全名单的旧值→新值，跳过的行和
    找不到的学号也逐条记，不截断。
- **时长承载**：每行直接成为这个人在这场活动里的那一笔 `HoursRecord`
  （`source="import"`，明细一段 `kind="import"`，时段写活动时间）。**不建隐藏场次**：
  `HoursRecord` 本来就只挂活动不挂场次，导出、我的志愿时长、申诉、锁定、外联确认都只认它；
  造假场次反而要在广场、签到、名额、冲突检测、档案里处处把它挑出来。
  之后的核准 → 本人确认/申诉 → 提交时长审核（含志愿北京名称）→ 外联确认 → 已完成与别的活动
  完全一样。时长管理页对它关掉「确认签退」与「手动加/扣」（没有签到可依据，改数去名单导入）；
  申诉采纳时导入那一段的数值同步改。
- **提示分**：没有签到，**导入名单即视为参与**，没有违规记录就加一次，时间记在活动结束时间；
  活动结束时间还没到就先不加。名单里的人可以登记违规，档案「参与过的活动」里也列出这类活动。

### 校外时长补登（`backend/routers/hours_claims.py`）

志愿者在校外**自行报名**参加的志愿活动，回来自己登记，**由对外联络部审批**后计入时长。

- **本人登记**（「我的志愿时长」页 →「登记校外活动」）：活动名称、活动日期（只填哪一天）、
  时长、服务描述、证明材料（图片或 PDF，≤3 份）、本人活动照片（≤3 张）、备注（选填）。
  两项材料都必填，单份 ≤5MB；要求**档案完整**（导出要身份证号与学院）；活动日期不能填将来；
  同名同天不能重复提交；每小时最多 3 条（去重与限频在按人的锁里查，同时点两次也只进一条）。
- **审批**（「活动审批」页 →「校外时长补登」）：对外联络部的值班人（没人值班发部长），
  会长团与管理员随时可办；通过时可**核定一个不一样的时长**（核减），驳回必须写理由。
  **审批人自己的补登要由别人批**：通知轮到提交人本人时往上找一层（值班人 → 部长 → 会长团），
  部长的值班日报里也列出补登。队列和证明材料只给上面这批审批人看（别的部长、不在班的骨干
  看不到）。提交后 48 小时（`APPROVAL_REMIND_HOURS`）没人处理催一次（值班人 + 会长团）。已通过的可以**撤销**（材料不实、
  重复登记、时长填错），撤销与通过都通知本人；审批人自己的那条也撤不了，要由别人撤。
- **一条独立的账**：不并进 `HoursRecord`——校外活动在平台上没有场次、报名和签到，塞进
  「一场活动一起结账」那套（核准 → 确认/申诉 → 提交审核 → 外联确认）会让活动的每条判断
  都要为它开岔路。通过的条目单独导出（「导出补登表」，含身份证号，下载留痕）给志愿北京录入；
  本人的「累计时长」把通过的补登加进去，明细单独一节。撤销的条目不再计入、也不导出。
- 证明材料与照片挂在 `Attachment`（`owner_type=claim_proof` / `claim_photo`，`activity_id` 留空），
  只有本人与能进「活动审批」页的人能看。提交、审批、撤回、撤销都记审计。

## 六、服装与学习材料

- **服装**（岗位设了「统一发放」才有）：一场活动**两个码**——一个领取、一个归还，
  直达 `/attire/{token}`。不做「同码扫两次」：领取和归还是两个物理动作，发生在活动的
  两头，现场常常是两张桌子。台账一人一条，另有批量登记与催领催还（可要求签收）。
- **学习材料**：挂在岗位上，文档自存（单文件 ≤50MB）或外链；视频不自托管，只存链接——
  大文件的上传成功率、带宽与备份代价都不划算。删记录即删文件，下载走票据。

## 七、导出与留痕

- 三类 Excel 导出，都在活动管理页：**排班表**（Sheet1 活动概览列场次清单，其后每场次一个
  Sheet：姓名/学号/学院/手机号/场次时间｜岗位组/岗位/组长/服务地点/接受调剂｜签到状态/
  签退时间，再按需接上报名问卷的答案列。表按现场的组织方式排——先按岗位分块、组长排头，
  还没排上的沉到表尾红字标出，一眼看得出还差谁；有志愿者时长的活动额外附一张时长页）、
  **时长记录**（给志愿北京录入用，姓名/学号/身份证号/时长/备注，选择了劳务的人不在其中）、
  **报名问卷结果**（一人一行、一题一列，供部长们在 Excel 里筛选）。
  导出内容里的公式一律先拆掉——志愿者填进去的东西不能当公式执行。
- 数据总览页顶部的**时间跨度同时驱动页面与导出**。页面里跟着它变的是四张卡：
  **活动总数**（区间内办过的活动，按活动结束时间，含补记录活动）、**有效报名**
  （区间内新产生的报名，按报名时间）、**累计时长(h)**（区间内活动的志愿时数）、
  **报名学院分布**（区间内新产生的在册报名）。其余是此刻或固定窗口，不随区间变：
  注册学生（全校）、报名中活动（此刻）、候补中（此刻）、24h内签到人次（最近一天）、
  近14天报名趋势（固定 14 天）、最近操作留痕（最新 8 条）。
- 同页的**活动汇总导出**（管理员 / 会长团）：选一个时间跨度，导出范围内每个活动
  一行——活动编号/名称/组织单位/联合主办方/时间/状态/志愿者人数（去重）/人次（各场次岗位报名之和，
  不去重）/志愿时数/劳务时数，末尾一行合计。区间按活动**结束时间**算（跨月的活动只落进
  一个区间，汇总加总不重复），补记录活动也算（时间取建活动时填的）。导出发的是数据，
  不产生通知。
- **审计留痕中心**：活动/场次/岗位增删改、发布、审批与转交、分配与强制分配、签到任务、
  导出、调分、违规登记全记录（字段级 diff）。部分日志对志愿者可见，
  在活动页公示摘要；其余按活动级可见范围过滤。
  - **时长变动按人记**：手动加减、删手动段、按签到确认、部分确认、申诉采纳、名单导入/
    修改/删除，每次都在变更明细里一人一条：哪位同学（姓名学号）、从几小时到几小时（结算
    合计）、原因或来源，不截断。「确认全部」只记数变了的人，部分确认记每个点名的人。
    志愿者自己选「志愿时长/劳务」不改合计，不在此列。明细超过 5 条时页面先折叠。

## 八、外部对接适配层（backend/integrations/）

两个适配器：`msgcenter` 消息中心 / `sso` 统一身份认证。
开关和参数都在 `.env`：`YVRUC_SSO_ENABLED`、`YVRUC_MSGCENTER_ENABLED` 填 `1` 启用真实
HTTP 调用，改完执行 `docker compose up -d` 重启后端生效。**开关已开但必填参数为空、
或推送通道里有短信（`1`），后端拒绝启动**，报错里写明改哪个变量。

演示模式行为：消息中心把模板消息落 `notifications` 表
（消息中心即收件箱，模板库 13 类场景），发送失败只标 `delivered=False`，不打断业务；
SSO 模拟「认证已通过」。

真实侧：`sso` 与 `msgcenter` 已备完整的 HTTP 实现。

志愿时长记在本平台、不对外回传。

### 意见反馈（`backend/routers/feedback.py`）

任何身份都能从右上角用户菜单（窄屏在抽屉底部）打开「意见反馈」，先选类型：

- **反馈平台问题**：正文必填、≤2000 字，可附 ≤3 张截图（png/jpg/webp，按文件头校验，
  单张 ≤5MB），一次表单提交落 `feedbacks` 表，截图挂 `Attachment`（`owner_type=feedback`）。
  每人每小时最多 5 条（Redis 固定窗口，超了 429）。弹窗「我的反馈」页签看自己提交的和回复。
- **反馈志愿问题**：平台不收，弹窗里给出「校青协志愿工作反馈平台」的链接，新窗口打开。

管理员身份在工作台「意见反馈」页按状态筛选、处理并回复，回复即发站内消息给提交人；
截图只有提交人本人与管理员看得到。提交与处理都记审计。

### 操作日志（`backend/oplog.py`）

和审计留痕分工不同：审计是业务代码在关键动作上写的一句人话，进数据库；操作日志在请求入口
（ASGI 中间件）统一采集，覆盖所有改数据的请求（POST/PUT/PATCH/DELETE）和登录（含失败）、
导出、附件下载（走直链下载依赖的接口）。浏览不记，请求正文不记，下载地址里的票据不记。
每条记时间、学号、姓名、当时的身份视角、IP、方法与路径、处理函数及其中文说明、活动 id 与
其余路径参数、状态码、耗时，需要时还有处理函数补的一句「改成了什么」（`oplog.mark_note`，
比如志愿者把调剂意愿改成了接受/不接受）。

- **存文件，不进数据库**：`YVRUC_OPLOG_DIR`（默认 `data/oplog`，compose 挂独立卷
  `yvruc_oplog`），JSON Lines，每个进程每天一个文件 `YYYY-MM-DD-<pid>.jsonl`，只追加、
  不轮转。请求线程只入内存队列，本进程的后台线程批量写盘，进程退出前把队列写完。
- **保留 180 天**：定时任务按文件名日期删除更早的文件。
- **磁盘剩余低于 1GB 停写**，站内通知全体管理员，每天一次（Redis 占位去重）。
- **查看**：管理员的「操作日志」页按学号或姓名、时间段（一次最多 31 天）、活动名称、
  操作类型筛选，分页，可导出 Excel。

### 平台公告（`backend/routers/platform.py`）

管理员在「平台公告」页编辑标题、正文和开关，全站只有一条（`announcements` 表，id 固定）。
启用后每个用户登录成功、第一次进入主框架时弹一次（前端在登录成功时打标记），点「知道了」
关闭；改了公告不会再弹给已登录的人。正文按纯文本显示，保留换行，http(s) 网址显示成链接。
修改公告不另写审计，修改请求本身进操作日志。
